# Plan 02-01: Category-Based Homepage Browsing

<objective>
Implement editable homepage category browsing so visitors can browse All Work plus dedicated sections such as UI/UX, Branding, Web, Visual Design, and Photography, while preserving the simple static text-file model and Phase 1 project card behavior.
</objective>

<requirements>
- CAT-01: Visitor can browse work grouped into dedicated homepage sections such as UI/UX, Branding, Web, Visual Design, and Photography.
- CAT-02: Visitor can still access an All view or equivalent complete project list without losing the simple portfolio overview.
- CAT-03: Project metadata can assign each project to one or more categories using beginner-editable text-file fields.
- CAT-04: Category section ordering and labels can be edited without changing JavaScript logic.
- PHOTO-01: Visitor can browse Photography as its own homepage category section.
</requirements>

<must_haves>
<truths>
- D-01: Categories appear as their own homepage sections, not only as filter chips.
- D-02: The homepage exposes an All Work view or equivalent complete list of all configured projects.
- D-03: Category sections reuse Phase 1 project cards: contained images, 4:3 media, title-only cards, desktop hover/focus title overlay, and mobile visible titles.
- D-04: The category UI remains calm and simple; no heavy dashboard, search panel, CMS, framework, or build step.
- D-05: Category labels and display order come from a beginner-editable config text file, not hard-coded JavaScript.
- D-06: Each project can be assigned to one or more categories through beginner-editable project text metadata.
- D-07: Projects with missing category metadata remain visible in All Work and fall into Other Work or a safe fallback rather than disappearing.
- D-08: Category metadata uses a minimal text-file convention that a template user can copy and edit.
- D-09: Photography is visible as its own homepage category section in Phase 2.
- D-10: Full multi-image photography entries are not implemented in this phase.
- D-11: The site remains plain HTML, CSS, JavaScript, and text files compatible with GitHub Pages.
- D-12: The homepage design follows the Phase 2 UI-SPEC spacing, typography, copy, and color contracts.
- D-13: Category section content does not overlap, cause horizontal scrolling, or hide project titles on mobile.
</truths>
<prohibitions>
- Do not introduce a package manager, framework, build pipeline, CMS, backend, or database.
- Do not implement Phase 3 photography gallery/detail behavior in this phase.
- Do not remove the complete all-project browsing path.
- Do not crop project thumbnail images to fill category cards.
- Do not render category/project text through new unsafe `innerHTML` templates when DOM/text APIs are sufficient.
</prohibitions>
</must_haves>

## must_haves

- D-01: Render categories as dedicated homepage sections.
- D-02: Keep All Work or an equivalent complete project list visible and accessible.
- D-03: Reuse Phase 1 card behavior and image containment inside every category grid.
- D-04: Keep category browsing visually quiet and simple.
- D-05: Make category ordering and labels editable from `Config/categories.txt` or an equally simple config text file.
- D-06: Add beginner-editable category metadata for each current project.
- D-07: Preserve visibility for projects with missing category metadata.
- D-08: Use a minimal text convention suitable for future template documentation.
- D-09: Include Photography as a visible category section.
- D-10: Leave multi-image photography entry behavior to Phase 3.
- D-11: Preserve GitHub Pages/no-build compatibility.
- D-12: Follow the UI-SPEC section layout, spacing, color, copy, and mobile constraints.
- D-13: Verify desktop and mobile layouts for no horizontal overflow and readable titles.

<threat_model>
Security exposure is low because this phase only reads static text files and renders category labels/project metadata on the homepage. Still apply these mitigations:
- Render category labels, descriptions, counts, and project titles with `textContent` or equivalent DOM text APIs.
- Do not add remote scripts, new CDNs, package dependencies, or third-party widgets.
- Preserve existing safe external-link behavior; do not create new `target="_blank"` links without `rel="noopener noreferrer"`.
- Treat malformed or missing category files as data errors with safe fallback UI, not as HTML injection surfaces.
Blocking threshold: high. No high-severity threats are expected if the mitigations above are followed.
</threat_model>
